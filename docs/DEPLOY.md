# Deploying Rental OS (free tier)

One web service serves both the API and the built frontend. The database is
external. Total cost to start: **zero**.

```
browser ──► rental-os.onrender.com ──► FastAPI ──► Neon Postgres
                    (serves the built SPA too)         (free, no expiry)
```

## Why it is shaped this way

The frontend is written same-origin — `frontend/src/lib/api.ts` calls relative
`/api/...` paths and Vite proxies them in development. So production keeps that
shape: `app/main.py::_mount_frontend` serves the built SPA from the API.

That removes two whole classes of deploy bug: there is no CORS configuration to
get wrong and no build-time API URL to keep in sync. It also means one instance
instead of two, which matters on a free tier.

## The one trap to know about

**Render's free PostgreSQL expires 30 days after creation** and is then
inaccessible unless you upgrade it ([docs](https://render.com/docs/free)). That
is fine for a demo and completely unacceptable for a rent ledger — a system of
record must not delete itself on a schedule.

So this blueprint deliberately declares **no Render database**. Use Neon, whose
free plan does not expire.

## Free-tier caveats (accepted, not hidden)

| Caveat | Effect | What to do |
|---|---|---|
| Free web service spins down after ~15 min idle | First request after a sleep takes ~1 min | Fine pre-production. Upgrade the instance before a demo or real use. |
| 5 GB bandwidth/month | Fat client bundles count against it | The build is ~1.1 MB of JS; fine for now. |
| Ephemeral filesystem | Uploaded documents are **lost on every redeploy** | Move to object storage before storing real documents. |
| Free DB connection caps | The app's default pool (30 + 5) is too big | The blueprint sets `DATABASE_POOL_SIZE=5`, `DATABASE_MAX_OVERFLOW=5`. |
| Render cron jobs | Pricing/availability needs checking against current plans — verify before relying on it | The monthly rent run should be a scheduled job; see "Not yet done". |

## Setup

### 1. Database — Neon (free, no expiry)

1. Create a project at [neon.tech](https://neon.tech), region close to your
   users (`eu-central-1` or `aws-eu-central-1` for Kenya).
2. Copy the **pooled** connection string and convert the driver:

   ```
   postgresql://user:pass@ep-xxx-pooler.eu-central-1.aws.neon.tech/rental?sslmode=require
   ↓
   postgresql+asyncpg://user:pass@ep-xxx-pooler.eu-central-1.aws.neon.tech/rental?sslmode=require
   ```

   Only the scheme changes. `app/core/database.py` translates `sslmode` into
   asyncpg's `ssl` argument and disables the prepared-statement cache on a
   pooler host automatically — you do not need to hand-edit the DSN further,
   and `alembic` reuses that same translation so migrations connect identically.

### 2. Deploy — Render

1. Render dashboard → **New → Blueprint** → pick this repository. Render reads
   `render.yaml`.
2. It will prompt for the two `sync: false` values:
   - `DATABASE_URL` — the DSN from step 1.
   - `ENCRYPTION_KEY` — generate it: `openssl rand -hex 32`
     (must be **64 hex characters**; Render's "generate" button produces a
     base64 string, which `bytes.fromhex()` rejects. Do not use it here.)
3. `SECRET_KEY` and `JWT_SECRET` are generated by Render.

### 3. Verify

```bash
BASE=https://rental-os.onrender.com

curl -s $BASE/health              # {"status":"up",...}
curl -s $BASE/api/v1/info         # {"name":"Rental OS","frontend_served":true,...}
curl -s -o /dev/null -w '%{http_code}\n' $BASE/          # 200, the SPA
curl -s -o /dev/null -w '%{http_code}\n' $BASE/api/v1/nope  # 404, never HTML
```

Then open `$BASE/` and log in with a seeded owner account.

`/health` is the health check path, so a container that starts but cannot serve
is reported unhealthy rather than staying up.

### 4. Local parity

```bash
docker build -t rental-os .
docker run --rm -p 8000:8000 \
  -e DATABASE_URL='postgresql+asyncpg://imani:imani@host.docker.internal:5432/rental' \
  -e ENCRYPTION_KEY="$(openssl rand -hex 32)" \
  -e SECRET_KEY="$(openssl rand -hex 32)" \
  -e JWT_SECRET="$(openssl rand -hex 32)" \
  rental-os
```

The image runs `alembic upgrade head` before serving, so a deploy can never
serve traffic against an older schema.

## Migrations

They run automatically on container start. To run them by hand against a
deployed database:

```bash
cd backend
DATABASE_URL='postgresql+asyncpg://...?sslmode=require' ./venv/bin/alembic upgrade head
DATABASE_URL='...' ./venv/bin/alembic current     # confirm the revision
```

Rollback is `alembic downgrade -1`. Note that a downgrade that drops a table
also drops its rows, and the free tier has no automatic backups — take a
`pg_dump` before any downgrade that touches data.

## Security gates before real use

Tracked in `secure/DEPLOYMENT_CHECKLIST.md`; the ones this deploy makes easy to
miss:

- [ ] `APP_ENV=production` — set by the blueprint, and it is what disables
      `/docs` and `/redoc`.
- [ ] `CORS_ORIGINS` — must be the real deployed origin, never `*`. Same-origin
      serving means this is mostly belt-and-braces, but the desktop shell and
      any future separate frontend will need it.
- [ ] `MPESA_CALLBACK_SECRET` — **unset today**, so
      `POST /payments/mpesa/callback` logs a warning and accepts unverified
      callbacks. Anyone who can reach the endpoint and guess a
      `CheckoutRequestID` can mark an invoice paid. Set this before taking live
      M-PESA traffic.
- [ ] `POST /payments/simulate` has no `APP_ENV` guard and marks an invoice
      paid with no money moving. Not exposed to tenants, but it is reachable by
      an owner token in production.
- [ ] Confirm no `.env` reaches the image. `.dockerignore` excludes
      `backend/.env` and `secure/`.

## Not yet done

- **No monthly rent-run job.** Rent is invoiced once at enrollment, so the
  books only ever contain each tenancy's first month. This is the highest-value
  missing piece and it is what the scheduled job would run.
- **No automated backups.** `pg_dump` on a schedule, before any real tenancy
  exists in it.
- **No CI.** Nothing runs on push. A CI run without a database would silently
  skip the 35 database-backed tests, so the workflow needs a Postgres service
  container to mean anything.
